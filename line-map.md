# Phaenon — Compiled layout and the line map (draft 0.1)

> Decided 2026-11-02 (roadmap D19). Until then the emitter kept line N of the `.php` on line N
> of the `.phn` (the *line rule*), so that every tool reporting a PHP position pointed into the
> source without a mapping. This document replaces that rule: the emitter lays out the PHP it
> generates as PER Coding Style wants it (PSR-12 until D22, 2026-11-04), and every compiled file
> carries a **line map** that the tools reporting positions read.

## 1. Why the line rule goes

PHP has no source maps: stack traces, warnings, PHPUnit, Xdebug, coverage, PHPStan and
`__LINE__` report the line of the code that ran. Keeping the lines identical made all of them
right with no tooling, and it was the cheapest start (M0). The price grew with every feature:

| Where | What the line rule forced on the output |
|---|---|
| D12 | line 1 carries `<?php`, the marker, `declare` and the namespace: four PSR-12 rules off |
| D11 | a compiler-added import shares a neighbour's line: `single_line_after_imports` off |
| D18 | `=> expr` compiles to a one-line `{ return …; }`, braces stay on the declaration line: `braces_position`, `class_definition` off |
| D18 | `@throws` from a `throws` clause and docblocks merged with it chained onto one line |
| `generics.md` | a generic declaration's docblock had to be a recorded exception |

The output stopped being "the PHP you would have written by hand" (D9) in its layout, and each
dogfood project carried a growing list of php-cs-fixer exceptions for its compiled trees.

The rule also saved less than it seemed. The code that runs is `.src/Foo.php`, not
`src/Foo.phn` (D12), so a stack-trace link, a breakpoint or a coverage view already needs
something that translates the *file*; the line rule only spared that something the line half of
the work. Debugging `.phn` in PhpStorm did not work under the rule either: PhpStorm sends the
breakpoint for `src/Foo.phn`, Xdebug runs `.src/Foo.php`, and path mappings work per directory
and cannot change the extension. PHP already has the precedent for compiled PHP plus a line
map: every compiled Twig template carries `getDebugInfo()`, Symfony's error page reads it, and
PhpStorm debugs Twig and Blade templates through such mappings.

## 2. The compiled layout

The emitter stays patch-based: plain PHP regions pass through as written, byte for byte. What
the compiler *generates* or *rewrites* it now lays out freely, so the output passes PER Coding
Style 3.0 (php-cs-fixer's `@PER-CS3x0`; PSR-12 until D22) with **no exceptions for compiled
trees**:

- **Header**: the open tag, the marker and `declare(strict_types=1)` each on their own line,
  separated by blank lines, before the source's first line:

  ```php
  <?php

  /* @generated by phaenon from Foo.phn */

  declare(strict_types=1);

  namespace App\Domain;
  ```
- **Imports the compiler adds** (D11) go on lines of their own, in their sorted place in the
  file's `use` block, or as a new block after the `namespace` statement, separated by one blank
  line as PER asks.
- **Docblocks the compiler writes or extends** (generics' `@template`/`@param`/`@return`,
  `@throws` from a `throws` clause, the types D14 puts back) are multi-line PHPDoc blocks, one tag
  per line, indented like the declaration. A source one-line docblock that gains tags becomes a
  multi-line block.
- **Expression bodies** `=> expr;` compile to a PER method body (`{` on its own line,
  `return expr;`, `}`); an expression that spans several lines in the source keeps its line
  breaks.
- **Opening braces of named functions, methods and class-likes** go where PER puts them (the
  next line, except after a multi-line parameter list, where `) {` share a line), whichever
  placement the `.phn` uses. Closures and anonymous classes keep theirs on the line, as in PER.
- **An empty body** — no statement, member or comment — stays as written: `{}` on the
  declaration's line is PER's abbreviation (§4 for class-likes, §4.4 for functions and methods)
  and Phaenon's layout (`functions.md` §5). Until D22 the emitter expanded it to PSR-12's
  `{` and `}` on lines of their own.
- **Closures the compiler writes** follow PER §7: an arrow function is `fn(…) =>`, with no space
  after `fn` (a partial application's, `spawn`'s); a `function` closure (a partial application
  whose parameter needs an inline `@var`, one in a constant expression) has `function (`, its
  statement one level in on a line of its own, and its closing brace on the next.
- **`__LINE__`** compiles to the source line as an integer literal, so code that reads it sees
  the `.phn` line.
- **The line map** is the file's last line (§3).

A compiled region the emitter does not touch keeps its layout: the `.phn` is the programmer's,
and the emitter is not a formatter.

## 3. The line map

### 3.1 Placement and syntax

Every file `phn build` compiles ends with one comment line:

```php
// phaenon-map v1 ../../src/Domain/Foo.phn 1-6=1 7:1 15-17=9 18:9 31-33=22 34:23
```

- `v1` is the format's version; readers ignore a map whose version they do not know.
- The path is the source file **relative to the compiled file's directory**, with `/`
  separators and `%20`, `%25` for a space and a percent sign. It resolves lexically, without
  touching the file system, so it holds in a container whose root differs from the build
  machine's.
- The entries cover the file's lines in ascending order; line numbers are 1-based:
  - `O:S` — **a run**: output line `O` is source line `S`, and each following output line is the
    next source line (`O+k` ↦ `S+k`) up to the next entry.
  - `O-P=S` — **a hold**: output lines `O` to `P` all map to source line `S`. They are lines the
    compiler wrote (the header, an import, docblock lines, the braces and `return` of an
    expanded body) or the continuation of a source line spread over several output lines.
- The map's own line is not covered. An output line after the last entry continues that entry's
  run, or its hold.
- A file that ends outside PHP mode (inline HTML after `?>`) ends with
  `<?php // phaenon-map …` instead, which outputs nothing. A file that uses
  `__halt_compiler()` carries the map on the line before that statement.
- A file without a valid map — hand-written PHP that `phn build` copies, or a map whose version
  a reader does not know — has no mapping: readers leave its positions as they are.
- Validity: tokens are separated by single spaces; the first entry starts at output line 1;
  entries ascend, never overlap, and the entry after a hold `O-P=S` starts at `P+1`; every number
  is at least 1 and written in decimal without leading zeros; `%20` and `%25` are the path's only
  escapes, and any other `%` makes the map malformed. A reader strips one trailing `\r` from the
  map's line before parsing it.

### 3.2 Lookups

- **Forward** (`.php` line → `.phn` line), for traces, logs, test failures and the debugger's
  current position: the entry with the largest `O` not above the line decides; a run adds the
  distance, a hold does not.
- **Reverse** (`.phn` line → `.php` line), for breakpoints and "show compiled code": the first
  output line of a *run* that covers the source line. Holds are never reverse targets, so a
  breakpoint never lands on a generated docblock or brace. A source line without a target (a line
  the compiler folded into another) takes the next source line that has one, as Xdebug resolves
  a breakpoint on a line without code.

### 3.3 Test vectors

The format has three readers (Go in `phn`, Kotlin in the plugin, PHP in `phaenon/runtime`) and
one writer. `internal/linemap/testdata/vectors.json` in the compiler repository is the
reference: maps, forward and reverse queries, and malformed maps a reader must reject. The
plugin and the runtime keep a copy and test against it; the compiler repository's freshness test
fails when a copy differs.

## 4. Who reads the map

### 4.1 The compiler

- **The emitter** records every edit's line delta and writes the map from them. Its old
  invariant ("an edit keeps its line count") becomes a property test over every golden: each
  source token that reaches the output is found on an output line whose forward lookup gives
  the token's source line.
- **`phn trace`** reads text from its arguments or stdin and rewrites the positions in it that
  point into compiled files with maps: `file.php:42`, `file.php(42)` (`getTraceAsString()`),
  `in file.php on line 42` / `file.php on line 42`, PHPStan's `--error-format=raw`. `--root
  /app=.` maps a production path prefix to the local checkout. `vendor/bin/phpunit | phn trace`
  and pasting a production trace both work. Since M6 it reads CI's formats too: GitHub workflow
  commands, and Checkstyle, JUnit, Clover and Cobertura reports (`tooling.md` §7.1).
- **The PHPStan parity test** and **the conformance execution suite** translate the lines they
  observe through the map instead of requiring identical lines, which makes the conformance
  corpus a large test of the map itself.

### 4.2 The PhpStorm plugin

- **Navigation**: a position in a compiled file — a stack-trace link in a Run or Test console, a
  PHPUnit failure location, a PHPStan or php-cs-fixer finding, a "go to line" from the compiled
  file's editor — opens the `.phn` at the mapped line.
- **Debugging, from the first release**: breakpoints are set in `.phn` files and sent to Xdebug
  for the compiled file at the reverse-mapped line; a suspended frame in a compiled file is shown
  in its `.phn` at the forward-mapped line; stepping steps by source line, continuing while the
  mapped line does not change; frames, variables, watches and evaluation work unchanged because
  the compiled code keeps every identifier (D9). The mechanism follows PhpStorm's template
  debugging for Twig and Blade where the platform allows it.

### 4.3 Production: `phaenon/runtime`

*`phaenon/debug` since 2026-11-08 (roadmap D24, T16): the package holds this and nothing else.*

- **`Phaenon\Debug\LineMap`** reads a compiled file's map (the last line, read once per file and
  process and cached) and answers both lookups. It is used on error paths only; a request that
  throws nothing never touches it.
- **A Monolog processor** translates the positions of a record's `context.exception`, its
  `previous` chain and every frame of their traces to `.phn` paths and lines, so every
  formatter (line, JSON, Logstash, the console) writes source positions.
- **A Sentry integration** translates the frames of an event's exceptions and stack traces and
  reads the context lines Sentry shows from the `.phn` when the source is deployed; with Sentry's
  code mappings the frames link to the `.phn` in the repository either way.
- Both are opt-in, registered in the application's configuration (for Symfony: a tagged
  service, and an entry in `sentry.options.integrations`). Monolog and the Sentry SDK are
  `suggest`ed, not required.

## 5. What changes elsewhere

- **php-cs-fixer**: the dogfood projects drop every compiled-tree exception (D12's line-1
  rules, D11's `single_line_after_imports`, D18's `braces_position` and `class_definition`).
- **Line-observing code**: `Reflection*::getStartLine()`, `debug_backtrace()` and
  `Throwable::getLine()` report compiled lines; code that compares them with a `.phn` line goes
  through the map (or `__LINE__`, which is exact). A fixture whose *compiled* line numbers a test
  asserts — PHPStan rule fixtures under `tests/PHPStan/Data` — is data, not code: it stays a
  `.php` file, which `phn build` copies as is.
- **Coverage**: PHPUnit's Clover and Cobertura reports go through `phn trace`, which counts every
  compiled line, holds included, as its source line (`tooling.md` §7.1). PhpStorm's coverage view
  still reports compiled lines (vault `open-items`).

## 6. Decisions

| # | Decision | Why |
|---|---|---|
| L1 | The emitter no longer keeps line N on line N; every compiled file carries a line map | §1 |
| L2 | The map is a comment on the file's last line, not a sidecar file or generated code | a sidecar can be lost or go stale between build and deploy; a method (Twig's `getDebugInfo()`) is an identifier the programmer did not write (D9); a trailing comment travels with the file and costs nothing at run time |
| L3 | Runs and holds, absolute line numbers, a relative source path | readable by a person looking at the file; holds are what keep breakpoints off generated lines; a relative path survives deployment |
| L4 | Generated and rewritten text follows PER Coding Style 3.0 (D22; PSR-12 until 2026-11-04); plain PHP regions stay as written | the output must read as hand-written PHP (D9), and the emitter is not a formatter |
| L5 | `__LINE__` compiles to the source line | the one position PHP code reads by itself must stay exact |
| L6 | Debugging in the plugin ships with the change, and the production integrations live in `phaenon/runtime` *(`phaenon/debug` since 2026-11-08, D24)* | debugging `.phn` needs a mapping in any case (§1); one package to require, and an integration loads only when its library is installed |

## 7. The canonical source layout (amends `functions.md` §5)

Decided with L1: **the opening brace of a class, interface, trait or enum keeps its own line**;
only a function's or method's brace stands on the declaration's line. A class costs one brace
line per file, a method one per method, and a class header (generic parameters with bounds, an
`implements` list with type arguments) is a file's longest line, where a trailing brace is hard
to see. `phn migrate` and the plugin's code style write it; `phn migrate` moves a class-like's
brace back down where an earlier run moved it up.
